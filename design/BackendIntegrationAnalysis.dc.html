Backend Integration Analysis - Sistema DA

Backend Integration Strategy

Análise Ducmb/studio + Opções de Implementação para Sistema DA

1. O que pode ser Aproveitado do Código Studio

✓ TIPOS (types.ts)

  • • User type (id, name, email, role, sector, status)
  • • Contract type (contrato, validade, object)
  • • Licitacao type (fase, prazo)
  • • Cotacao type (responsável, fase)
  • • Ferias type (datas, tipo)

⚠ LIMITAÇÕES

  • • Não tem tipos para Produtos/Inventário
  • • Não tem tipos para Protocolo/Documentos
  • • Não inclui Auditoria/Logs
  • • Sem definição de Permissões por módulo
  • • Dados são mock (array local)

data.ts: Fornece estrutura de dados mockada (users array). Não há API calls, tudo é local. Pode servir como referência de schema, mas requer expansão significativa.

utils.ts: Apenas utilitário CSS (clsx + twMerge). Não oferece valor para lógica de negócio do Sistema DA.

2. Gaps no Código Studio para Sistema DA

Recurso Studio Oferece? Sistema DA Precisa? Solução
Tipos de Usuário com Roles ✓ Básico ✓ Sim Estender: adicionar permissions[] e department
Tipos de Produto/Inventário ✗ Não ✓ Sim Criar novo type: Product { code, name, stock, category }
Tipos de Protocolo/Documento ✗ Não ✓ Sim Criar: Document, Process, Deadline types
Auditoria & Logs ✗ Não ✓ Sim Criar: AuditLog { userId, action, timestamp, details }
RBAC com Permissões ~ Parcial ✓ Sim Estender User: permissions: { compras, rh, protocolo, almoxarifado }
API Endpoints ✗ Não ✓ Sim Definir contratos REST + implementar

3. Opções de Implementação Backend

A

Opção A: Expandir Studio + Integração Gradual

Leveraging existing Studio codebase

Abordagem: Estender types.ts com Product, Document, AuditLog. Criar endpoints Node.js/Express que validam contra esses tipos. Integrar gradualmente cada módulo (DC) com chamadas fetch() para a API.

Vantagens: Reutiliza scaffold Studio, incremental, baixo risco.
Desvantagens: Requer refator significativo dos types Studio. Lentidão no desenvolvimento.

✓ Pré-requisitos

  • • Fork/clone Studio repo
  • • Estender types.ts
  • • Node.js + Express backend
  • • PostgreSQL ou MongoDB

Esforço Estimado

4-6 semanas

(types + endpoints + testes)

B

Opção B: Fresh Start com Supabase/Firebase

Backend-as-a-Service approach

Abordagem: Descartar Studio backend, usar Supabase (PostgreSQL gerenciado + Auth + RLS) ou Firebase. DCs fazem chamadas diretas ao Supabase via client libs. Zero código backend.

Vantagens: Rápido, sem manutenção de servidor, Auth nativa, RLS para RBAC automático.
Desvantagens: Vendor lock-in, custo per-user, menos controle sobre lógica.

✓ Setup

  • • Conta Supabase/Firebase
  • • Schema SQL no console
  • • Client SDK no DC
  • • RLS policies

Esforço Estimado

2-3 semanas

(setup + schema + integração DC)

C

Opção C: Definir API Contract + Mock Ativos Preparados

Spec-driven development

Abordagem: Documentar OpenAPI/Swagger de todos endpoints. DCs continuam com mocks (localStorage), mas estrutura fetch() preparada. Backend implementa depois sem quebrar DC.

Vantagens: Parallelização Dev/Backend, contrato claro, testável, backend agnóstico.
Desvantagens: Mais planning upfront, requer sincronização Dev/Backend.

✓ Entregáveis

  • • OpenAPI spec (YAML)
  • • Mock responses (JSON)
  • • DC fetch() stubs
  • • Error handling guide

Esforço Estimado

1-2 semanas

(spec + mocks + DC stubs)

✓ Recomendação: Opção B + C Híbrida

Fase 1 (1-2 semanas): Implementar Opção C—definir OpenAPI spec completo (auth, inventory, RBAC, protocolo), criar mock responses, preparar stubs fetch() nos DCs. Entregas: Spec YAML, mocks JSON, DC com fetch() condicional (mock || API).

Fase 2 (3-4 semanas): Backend paralelo: escolher Supabase (rápido, produção pronta) OU Node.js+Express (controle máximo). Implementar endpoints conforme spec. DCs apontam para API real quando pronto. RBAC nativo (Supabase RLS ou custom middleware).

Benefícios: DCs continuam funcionando com mocks durante Fase 1. Backend teams trabalham em paralelo. Integração é just-swap-endpoints. Studio code reutilizado minimamente (types base apenas). Menos risco de quebra.

4. Próximos Passos Imediatos

  1. Escolher opção: A (estender Studio), B (Supabase), ou C (spec-first).
  2. Se Opção C: Gerar OpenAPI spec completo (endpoints auth, RBAC, inventory, protocolo, RH).
  3. Se Opção B: Criar Supabase project, definir schema SQL (users, products, documents, audit_logs).
  4. Se Opção A: Fork Studio, estender types.ts com novos tipos, criar Node.js boilerplate.
  5. Integração DC: Adicionar fetch() handlers em cada DC conforme fase 2.
  6. Testes: Unit tests para RBAC, validação de dados, audit logging.
